# 코드 탐색 라우팅 규칙 — 설계 근거

`codegraph-usage.md`의 규칙별 설계 결정과 근거를 기록한 문서다. 규칙을 바꾸면 이 문서의 해당 항목도 함께 고치고, 결정이 바뀐 경우에는 "변경 이력"에 남긴다.

근거 태그는 다음과 같다.
- **[실측]:** 아래 "측정 환경"에서 직접 잰 값
- **[소스]:** codegraph 소스 코드를 확인한 내용
- **[문서]:** codegraph README에서 확인한 내용
- **[추정]:** 측정하지 않은 추론
- **[판단]:** 트레이드오프를 보고 내린 선택

## 배경

graph 인덱싱은 구조 파악과 호출 체인 추적에는 강하다. 반면 경로를 아는 파일이나 단순 문자열 검색에서는 grep/Read보다 비싸다. 그래서 도구를 하나로 몰지 않고, 질문 유형별로 도구를 나누는 라우팅 규칙을 두기로 했다.

검토했다가 버린 대안은 넷이다.
- **explore를 완전히 끄는 방식:** 이름을 모르는 탐색에서 왕복 횟수가 늘어난다(R6 근거 참고).
- **explore 중복 제거(`CODEGRAPH_EXPLORE_DEDUP=1`):** 응답 크기가 거의 줄지 않고, 요약 이후 모델이 갖고 있지 않은 소스를 생략할 위험이 있다(R7 근거 참고).
- **steering을 `inclusion: fileMatch`(`**/*.java`)로 전환:** 턴당 약 1,400 토큰을 아낄 수 있지만, Java 파일을 열기 전의 첫 탐색 질문에서 규칙이 빠진다. 가장 자주 쓰는 탐색 질문에서 규칙이 빠지면 서버 지침대로 explore부터 부르게 되므로 `always`를 유지한다 [판단].

## 턴당 고정 비용

도구 정의, 서버 지침, `always` steering은 매 턴 모델 입력에 다시 들어간다. explore 결과도 한 번 들어오면 이후 매 턴 다시 읽힌다. 그래서 비용은 "턴당 크기 × 남은 턴 수"로 비교한다.

| 항목 | 크기 | 턴당 토큰(어림) | 우리 선택으로 줄일 수 있나 |
| --- | --- | --- | --- |
| 서버 지침(MCP `initialize`) | 6,718자 | 약 1,700 | 없음. 끄는 옵션이 없다 [소스] |
| steering 규칙(`always`) | 2,712자(한글 907자) | 약 1,400 | 규칙 길이로만 |
| 도구 정의 4개 | 5,049자 | 약 1,260 | 도구 수로 |
| 합계 | | 약 4,300 | |

- 근거 문서(`manual`, 약 8,300자, 약 4,600 토큰)는 불러올 때만 든다.
- [추정] 토큰은 한글 1자 ≈ 1토큰, 그 밖의 문자 4자 ≈ 1토큰으로 어림했다. 프롬프트 캐시가 적용되면 비용은 크게 줄지만 컨텍스트 창 점유는 그대로다. Kiro가 캐시를 쓰는지는 확인하지 못했다.
- [판단] codegraph를 쓰지 않는 세션(문서·설정 작업)에서는 약 4,300 토큰이 턴마다 그대로 낭비된다. 이를 피하려면 그 세션에서 MCP 서버를 꺼야 한다. 그런 세션이 드물다면 감수한다.

T턴 세션의 k번째 턴에서 explore(약 6,200 토큰)를 한 번 피했을 때의 손익분기는 다음과 같다.

| 결정 | 턴당 비용 | 손익분기 |
| --- | --- | --- |
| 좁은 도구 3개(callers·callees·impact) | 약 820 | k ≤ 0.87T |
| callees 단독 | 약 270 | k ≤ 0.95T |
| steering `always` | 약 1,400 | k ≤ 0.78T |

세션의 앞쪽 78% 안에 관계 질문(호출자, 흐름, 영향도)이 한 번만 나와도 세 결정 모두 이득이다. Java/Spring 코드 작업 세션이라면 거의 항상 나온다.
- **메인 저장소와 워크트리에 도구 세트를 다르게 주는 방식:** `.worktrees/`가 메인 저장소 안에 있어서 MCP 프로세스가 1개만 뜬다. 도구 허용 목록은 프로세스 단위라서 저장소별로 나눌 수 없다 [실측]. 결국 도구 수를 동적으로 바꾸는 대신 규칙으로 제한하기로 했다 [판단].

## 규칙별 근거

### R1. 서버 지침보다 우선
- [소스] codegraph는 MCP `initialize` 응답으로 약 6,700자의 지침을 보낸다(`src/mcp/server-instructions.ts`). 그 안에 "Read/grep 대신 explore를 써라", "경로를 아는 파일도 explore로 읽어라", "grep으로 재검증하지 마라"가 있다. 이 문서의 규칙과 정면으로 충돌한다.
- [추정] Kiro가 이 서버 지침을 모델에 어떻게 반영하는지는 확인하지 못했다. 반영되지 않더라도 우선순위를 명시해 두는 데 손해는 없다.

### R2. 도구를 4개로 고정 (`CODEGRAPH_MCP_TOOLS=explore,callers,callees,impact`)
- [소스] 기본 설정에서는 explore만 노출된다. 다른 도구는 환경변수로 켜야 한다.
- [실측] 도구 정의 크기는 callers 1,125자, callees 1,081자, impact 1,057자, explore 1,786자다. 좁은 도구 3개의 정의는 턴당 약 820 토큰이다. 세션 앞쪽 87% 안에서 explore를 한 번만 피해도 남는다("턴당 고정 비용" 절 참고).
- [실측] `callees`는 "X에서 Y까지" 흐름 질문에서 explore보다 정확하고 싸서 포함한다(R16 근거 참고). 초안(2026-10-31)에서는 근거 없이 빠져 있었다.
- [실측] `search`는 제외했다. Java 클래스명은 대체로 고유해서 grep으로 충분하다고 판단했다.
- [실측] `node`도 제외했다. 파일 모드 결과가 Read와 크기가 같았다(12,037자 대 원본 11,227자). 도구 정의는 2,951자로 가장 크다.
- [문서] codegraph 작성자는 메뉴가 길면 에이전트가 도구를 잘못 고른다는 측정을 근거로 explore 하나만 노출했다. 다만 그 측정은 아키텍처 질문 하나짜리 벤치마크라, 호출자나 영향도 같은 중간 질문은 다루지 않았다. 그래서 질문 유형마다 도구가 하나씩 대응하도록 메뉴를 4개로 최소화했다 [판단].

### R3. 가장 싼 도구부터
- [실측] 질문이 달라도 explore 응답은 매번 약 24,900자(약 6,200 토큰)였다. 상한까지 채워 반환하는 구조로 보인다. 같은 질문에 callers는 147–164자(약 40 토큰), impact는 580자(약 145 토큰), callees는 147–759자(약 36–189 토큰)였다.
- [문서] codegraph README는 처리 토큰은 62% 줄지만 세션 끝 잔류 컨텍스트는 약 80% 늘어난다고 스스로 밝힌다.

### R4. grep 30건 기준과 callers로의 전환
- [실측] `UmsAdminService.delete` 호출자를 grep `\.delete(`로 찾으면 31줄(4,402자) 중 관련된 줄이 1줄이었다. callers는 정확히 1건을 반환했다.
- [판단] "30건"은 이 측정에서 잡은 경험칙이다. 사내 코드에 맞춰 조정한다.

### R5. 상황별 도구
- 경로를 아는 파일 → Read: [실측] 그래프로 읽어도 크기가 Read와 같다.
- 문자열 검색 → grep: [추정] 그래프는 심볼 단위로 인덱싱해서 문자열 자체를 찾지 않는다.
- 클래스·메서드 위치 → grep: [추정] Java에서는 결과가 적다. `search`를 제외한 결정(R2)과 연결된다.
- 비코드 파일 → grep/Read: [문서] yml, properties, XML은 codegraph 지원 언어 목록에 없다.
- 호출자 → callers: [실측] 약 40 토큰이고 흔한 이름에서도 정확했다.
- 호출 흐름 → callees: [실측] R16 근거 참고.
- 영향 범위 → impact: [실측] `PmsBrandService.deleteBrand`의 오버로드 2개를 합쳐서, `GET /brand/delete/{id}`와 `POST /brand/delete/batch` 라우트까지 약 145 토큰에 반환했다.

### R6. explore는 이름을 모를 때만
- [실측] 로그인 흐름을 이름을 아는 상태에서 좁은 도구로 재구성하면 5번 호출에 합계 약 1,770 토큰이었다. explore는 1번 호출에 약 6,200 토큰이었다.
- [추정] 대신 호출 1번마다 전체 컨텍스트를 다시 읽는다. 기본 컨텍스트를 2만 토큰으로 가정하면 처리 토큰은 explore 쪽이 약 4.6만, 좁은 도구 쪽이 약 12.5만이다. 이름을 모르면 탐색 왕복이 더 붙는다.
- [판단] 이름을 모를 때는 왕복을 줄이는 explore가 낫고, 이름을 알면 잔류 컨텍스트가 적은 좁은 도구가 낫다.

### R7. 주제당 1회, 결론 요약
- [실측] 응답 하나가 약 6,200 토큰이라 같은 영역을 반복 호출하면 누적된다.
- [소스] 호출 간 중복 제거 옵션(`CODEGRAPH_EXPLORE_DEDUP=1`)이 있지만 **채택하지 않는다.** 반복 호출 문제는 이 옵션이 아니라 R7 규칙으로 막는다.
- [실측] dedup은 응답을 줄이지 않는다. 이미 보낸 소스를 "Already sent" 표시로 바꾸고, 비운 자리를 아직 안 보낸 다른 소스로 채운다. 한 세션에서 연속 3회 호출했을 때 결과는 다음과 같다.
  - 1회차: 끔·켬 모두 24,979자
  - 2회차(겹치는 질의): 끔 24,925자, 켬 24,931자
  - 3회차(같은 질의): 끔 24,979자, 켬 22,052자(−12%)
- [소스] dedup 상태는 MCP 연결 단위로 유지되고, 그 연결에서 보낸 내용을 모델이 아직 갖고 있다고 가정한다. codegraph도 "연결당 하나의 지속 컨텍스트를 보장하는 호스트에서만" 쓰라고 명시한다.
- [추정] Kiro는 컨텍스트가 차면 대화를 요약한다. 요약 뒤에는 모델이 원문을 잃는데 서버는 "이미 보냈다"는 표시만 주므로, 다시 Read하거나 없는 내용을 근거로 진행할 위험이 있다. Kiro IDE의 여러 채팅이나 spec 세션이 MCP 연결 하나를 공유하는지도 확인하지 못했다.
- [판단] R7로 반복 호출이 드물어 이득은 작고, 위 위험은 크다.

### R8. 질의에 이름 포함
- [실측] 자연어 질의("how does admin login and JWT token issuance work")에서는 핵심인 `UmsAdminServiceImpl.login` 본문이 빠지고 "Not shown" 목록으로 밀려났다. 그 자리는 `UmsAdminLoginLog`의 getter가 채웠다.
- [실측] 이름을 넣은 질의에서는 흐름과 `UmsAdminService.login → UmsAdminServiceImpl:98` 구현체 연결이 함께 나왔다.
- [실측] "who calls UmsAdminService.delete"로 질의하자, 무관한 `SmsFlashPromotion*Controller.delete` 등을 단어 매칭으로 끌어왔다.
- [소스] explore는 의미가 아니라 이름과 단어를 어휘적으로 매칭한다.

### R9. spec 구현 중 explore 금지
- [판단] 탐색은 spec·design 단계에서 끝내고, 구현 단계에서는 문서에 기록된 이름을 쓴다. 긴 구현 세션에 큰 응답이 쌓이는 것을 막기 위해서다.

### R10. 워크트리는 projectPath 필수
- [실측] MCP 서버는 메인 저장소에서 1개만 뜨고, 워크트리 DB는 `projectPath`로 열린다.
- [실측] 워크트리에서 새 호출자를 추가하자 `projectPath`를 준 조회에는 약 1.5초 뒤 반영됐다(호출자 2건). `projectPath` 없이 조회하면 메인 DB 결과가 그대로 나왔다(1건).
- [실측] `.worktrees/`가 gitignore에 제대로 등록돼 있지 않으면 메인 데몬의 watcher가 워크트리에서 수정된 파일을 메인 DB에도 넣어 결과가 중복된다. `git check-ignore .worktrees/x`로 확인한다.

### R11. 인터페이스와 구현체 함께 조회
- [실측] `UmsAdminService.getAdminByUsername`의 callers는 컨트롤러 1건만 반환했다. 그러나 grep으로 보면 `UmsAdminServiceImpl` 126행과 267행에서도 호출한다.

### R12. 영향 범위 확정 시에만 grep 교차 확인
- [실측] Spring 특유의 연결이 아닌 평범한 메서드 호출도 그래프에서 빠질 수 있다. `jwtTokenUtil.generateToken(userDetails)` 호출 2곳(admin·portal 서비스 구현체)이 callers와 callees 어디에도 잡히지 않았다. 같은 필드를 통한 `refreshHeadToken`, `getUserNameFromToken` 호출은 모듈을 넘어서도 잡혔다. `generateToken`이 오버로드된 메서드라는 점이 의심되지만, 오버로드인 `deleteBrand`는 정상이어서 원인은 확정하지 못했다. 영향 범위 확정 시 grep 교차 확인이 필요한 직접 근거다.
- [추정, 미검증] 목록은 정적 분석의 일반적인 한계에 근거한 것이다. codegraph가 각 항목을 실제로 놓치는지는 확인하지 않았다. 사내 코드로 확인해서 잘 잡히는 항목은 지운다.
- [문서] codegraph의 자체 측정에서 Spring 라우트 인식률은 83.3%다.
- [판단] 교차 확인을 영향 범위 확정 시로만 제한하는 것은 매 탐색마다 재검증하는 비용을 피하기 위해서다.

### R13–R15. 인덱스 신선도
- [실측] 파일 수정 1.5초 뒤 조회에서 R13의 배너가 나왔고("edited 1563ms ago, indexing in progress"), 4초 뒤에는 사라졌다.
- [소스] DISABLED/RECOVERING 배너의 의미와 `init`을 사용자에게 맡기라는 내용은 codegraph 서버 지침에 있다.

### R16. 호출 흐름은 callees로 한 단계씩
- [실측] `UmsAdminController.login`에서 `JwtTokenUtil.generateToken`까지를 두 방식으로 비교했다. 실제 경로는 컨트롤러 → `UmsAdminService.login`(인터페이스) → `UmsAdminServiceImpl.login` → `jwtTokenUtil.generateToken()`이다.
  - callees 한 단계씩: 3번 호출(759자, 147자, 486자, 합계 약 350 토큰)로 구현체까지 도달했다. 구현체의 callees 목록에 `generateToken`이 없어서 끊긴 지점이 바로 드러났다.
  - explore(X와 Y 이름 지정): 24,972자(약 6,200 토큰). 흐름(Flow) 절이 아예 없었고, 경로를 찾지 못했다는 표시도 없이 관련 소스로 채워졌다.
- [실측] 인터페이스 메서드(`UmsAdminService.login`)에 callees를 걸면 구현체(`UmsAdminServiceImpl.login`)를 반환했다. Spring 서비스 계층을 넘는 데 문제가 없다.
- [판단] callees는 실패가 드러나는 방식으로 실패하고(목록에 다음 메서드가 없음), 그 지점의 메서드 본문 Read로 복구할 수 있다. explore는 큰 비용을 쓰고도 실패가 드러나지 않는다. 그래서 X의 이름을 알면 callees를 기본으로 한다.

## 측정 환경

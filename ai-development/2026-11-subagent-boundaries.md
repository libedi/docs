## TL;DR

- **글의 핵심은 "단일 에이전트가 더 낫다"가 아니라 "서브에이전트 경계를 조직도가 아니라 컨텍스트에 맞춰라"입니다.** 기본값은 단일 루프가 스킬(절차)과 도구(하드 제약)를 필요할 때 불러오는 구조이고, 서브에이전트는 필요가 확인될 때만 남깁니다. 이 방향에 동의합니다.
- **구조는 마이크로서비스에서 모듈러 모놀리스로 돌아온 흐름과 같습니다.** 서브에이전트는 서비스, 스킬은 모듈, 핸드오프 요약은 직렬화 손실입니다. 서로 강하게 엮인 서브에이전트는 분산 모놀리스입니다.
- **아래 보완은 글의 결론을 뒤집지 않습니다.** 대부분 사례가 특정 도메인에 치우쳐 있고 기준이 모호하다는 지적입니다. 하나는 모호함을 넘어섭니다. "합쳐서 나빠지지 않으면 합쳐라"라는 측정 기반 판단이 모든 경계에 통하지는 않습니다.
- **"컨텍스트" 경계는 용량, 독립성, 신뢰의 세 종류입니다.** 용량 경계는 평가로 정하고, 독립성·신뢰 경계는 평가 결과와 상관없이 원칙으로 고정합니다. 글이 규칙에 적용한 "절차는 스킬, 제약은 도구"의 구분을 아키텍처 경계에도 적용한 것입니다.
- **페르소나 기반 멀티 에이전트가 틀린 이유는 사람 조직이 분업하는 이유를 보면 드러납니다.** 전문성 때문에 하는 분업은 에이전트로 옮겨오지 않습니다(모두 같은 모델이고, 전문성은 스킬로 불러옴). 반면 직무 분리처럼 통제를 위한 분업은 그대로 옮겨옵니다.
- **기존 위임 기준의 수정을 제안합니다.** ① 컨텍스트 격리는 세 종류로 나누고, ② 절차 표준화는 서브에이전트가 아니라 스킬을 만들 이유로 옮깁니다.

## 1. 글의 주장

### 1.1 핵심 주장

여러 기업 배포를 비교해 보니, 스킬을 갖춘 단일 에이전트가 프롬프트 하나로 모든 것을 처리하는 설계와 서브에이전트 설계 모두보다 품질이 자주 높았고, 대개 과제당 비용과 지연도 낮았다고 합니다. 서브에이전트 자체를 부정하지는 않지만, 모든 팀과 모든 문제 유형의 기본값이 되어서는 안 된다는 입장입니다.

나눌 때는 문제 유형이나 팀이 아니라 컨텍스트를 기준으로 나누고, 서브에이전트에는 나머지 시스템을 거의 몰라도 되는 일을 맡기고 짧은 결과만 받으라고 합니다.

### 1.2 대기업에서 반복되는 실패 패턴

| 패턴 | 내용 |
| --- | --- |
| 컨텍스트 손실 | 에이전트 사이를 오가며 세부가 빠짐 (글의 표현으로 "전화 게임") |
| 서브에이전트 난립 | 기준도 소유자도 없는 중복 서브에이전트가 쌓임 |
| 프랑켄프롬프트 | 팀마다 시스템 프롬프트에 규칙을 덧붙여 충돌하고 어조가 흔들림 |
| 국소적 평가 | 팀별 하위 과제에 맞춘 평가가 쌓여 전체 점수가 흐려짐 |
| 지연 | 서브에이전트마다 모델 루프가 중첩됨. 한 고객사는 단일 루프가 약 2배 빨랐음 |

### 1.3 서브에이전트를 유지할 조건

1. 단일 루프에서 컨텍스트 비대화로 인한 성능 저하가 측정될 때
2. 여러 일을 병렬로 처리하고, 끝나면 버릴 새 컨텍스트가 필요할 때
3. 단일 에이전트가 도구를 잘못 고르거나 시스템 프롬프트의 지시가 서로 충돌할 때

### 1.4 단일 루프 설계

- 모델 하나, 컨텍스트 하나로 열린 도구 루프를 돌리고, 턴·비용 예산과 쓰기 게이트는 하네스에서 정합니다.
- 모델이 계획을 세우고, 결과에 따라 중간에 고칩니다.
- 도메인 절차는 **스킬**로, 검증·승인 같은 하드 제약은 **도구**로, 항상 필요한 값싼 로딩과 기계적인 작업은 **코드**로 둡니다.
- 도구는 API 단위가 아니라 사용자 의도 단위로 묶습니다. 도구 정의가 30~50개를 넘으면 도구 선택이 나빠지는 경향이 있다고 합니다.

### 1.5 전환 방법

1. 평가부터 만듭니다. 골든 예제 10개로도 시작할 수 있습니다.
2. 가장 많이 쓰이거나 함께 호출되는 서브에이전트부터 하나씩 합칩니다.
3. 중간 단계로 서브에이전트를 도구처럼 호출합니다. 응답 스키마를 통일하고 결과를 실제 데이터로 검증할 수 있습니다. 완전한 핸드오프는 서브에이전트가 사용자와 직접 대화해야 할 때만 씁니다.
4. 총점이 아니라 과제별로 결과가 바뀐 것을 비교합니다. 한 사례에서는 합친 뒤 지연은 줄었지만 배송일 확인 절차가 깨졌고, 그 실패는 두 번 실행 중 한 번에만 나타났습니다.

조직 운영으로는 소규모 중앙 팀이 시스템 프롬프트와 end-to-end 품질을 소유하고, 도메인 팀은 스킬·도구·평가를 기여하며 각자 책임자(DRI)가 되는 구조를 권합니다.

## 2. 동의하는 부분: 마이크로서비스 교훈의 재연

### 2.1 서브에이전트는 서비스, 스킬은 모듈

| 마이크로서비스 | 에이전트 |
| --- | --- |
| 서비스 간 호출의 직렬화 | 핸드오프 요약의 정보 손실 |
| 네트워크 홉 | 중첩된 모델 루프의 지연 |
| 분산 모놀리스 (서로 강하게 엮인 서비스) | 서로의 출력에 연쇄적으로 의존하거나 같은 데이터를 만지는 서브에이전트 |
| 모듈러 모놀리스 (Spring Modulith 등) | 스킬을 필요할 때 불러오는 단일 루프 |
| MonolithFirst | 단일 루프부터 시작하고, 이유가 생기면 서브에이전트로 추출 |

**근거**

- 글이 합칠 대상으로 꼽는 "서로 강하게 결합된 전문 에이전트"는 분산 모놀리스의 냄새와 같습니다. 경계가 비용만 만들고 독립성은 주지 못하는 상태입니다.
- 성공한 마이크로서비스는 대부분 커진 모놀리스를 쪼개면서 시작했다는 관찰([Fowler, MonolithFirst](https://martinfowler.com/bliki/MonolithFirst.html))이 에이전트에서도 성립합니다. 경계가 어디서 안정되는지는 써 봐야 압니다.

### 2.2 소유 경계와 실행 경계의 분리

이 글에서 가장 좋은 통찰입니다. 도메인 팀은 서브에이전트가 아니라 스킬·도구·평가를 소유합니다. 하나의 코드베이스 안에서 CODEOWNERS로 소유권을 나누는 것과 같습니다.

**근거**

- 팀 소유를 실행 경계로 표현하면 콘웨이 법칙대로 조직도가 아키텍처가 됩니다. 소유권은 실행 경계 없이도 표현할 수 있으므로, 실행 경계는 런타임에 실제로 필요한 이유가 있을 때만 둡니다.

### 2.3 절차는 스킬, 제약은 도구

상황에 따라 해석하는 절차는 스킬로, 절대 깨지면 안 되는 제약은 도구와 훅으로 둡니다. 스펙 3층 구조(불변 제약 / 수락 기준 / 구현 계획)에 대응시키면, **불변 제약은 스킬이 아니라 훅이나 도구로 강제해야 합니다.**

**근거**

- 스킬은 모델이 읽고 따르는 지시라서 지켜질 가능성이 높을 뿐 보장되지는 않습니다. 지시만으로 에이전트의 행동이 막히지 않는다는 관찰은 [에이전트 코드 리뷰 제안](2026-11-agent-code-review-stage.md) 4.2절에 정리했습니다.

## 3. 보완 1: 실패 패턴 중 셋은 거버넌스 문제

다섯 가지 실패 패턴 중 난립, 프랑켄프롬프트, 국소적 평가는 전체를 책임지는 주인이 없어서 생깁니다. 아키텍처를 바꿔서 해결되는 것은 컨텍스트 손실과 지연 두 가지입니다.

| 패턴 | 원인 | 단일 루프로 합치면 |
| --- | --- | --- |
| 컨텍스트 손실 | 아키텍처 | 해결됨 |
| 지연 | 아키텍처 | 해결됨 |
| 난립 | 거버넌스 | 스킬 난립으로 옮겨감 |
| 프랑켄프롬프트 | 거버넌스 | 스킬 설명과 공통 프롬프트로 옮겨감 |
| 국소적 평가 | 거버넌스 | 평가 소유자가 없으면 그대로 남음 |

**근거**

- 거버넌스 없이 합치면 증상이 스킬로 옮겨갑니다. 글이 스킬의 비용과 사용 빈도를 보여 주고 정리하는 `/skill-doctor`를 함께 소개하는 것도 이 때문입니다.
- 글도 후반부에서 중앙 팀 소유 구조를 처방으로 제시하므로 결론과 충돌하지는 않습니다. 진단(아키텍처)과 처방(조직)의 연결이 느슨하다는 지적입니다. 실무적으로는 **중앙 소유와 end-to-end 평가를 먼저 세워야** 합친 효과가 유지됩니다.

## 4. 보완 2: 컨텍스트 경계는 세 종류

### 4.1 세 가지 경계

글은 "컨텍스트 기준으로 나눠라"라고 한마디로 말하지만, 서브에이전트로 나누는 이유는 서로 다른 세 가지입니다.

| 경계 | 나누는 이유 | 예 | 판단 방법 |
| --- | --- | --- | --- |
| 용량 | 담을 양이 너무 많아 압축이 필요함 | 대량 코드 탐색 후 요약만 반환 | 평가로 정함 (글의 기준 그대로) |
| 독립성 | 검증자가 생성자의 추론을 보면 안 됨 | 코드 리뷰, 테스트 작성자와 구현자 분리 | 원칙으로 고정. 합치려면 근거가 필요함 |
| 신뢰 | 신뢰할 수 없는 입력을 격리함 | 외부 문서·웹 처리를 쓰기·전송 도구 없이 수행 | 원칙으로 고정. 평가로 판단하지 않음 |

병렬성은 이와 별개인 처리량의 이유이고, 글의 조건 2에 해당합니다.

### 4.2 "합쳐서 나빠지지 않으면 합쳐라"가 통하지 않는 곳

**독립성 경계**

- 생성할 때는 공유된 컨텍스트가 장점이지만, 검증할 때는 버그입니다. 같은 컨텍스트의 검증자는 생성자의 출력뿐 아니라 그 출력을 만든 추론까지 공유합니다. LLM 평가자는 자기가 생성한 출력을 더 높게 평가하는 경향이 있습니다([Panickssery et al., 2024](https://arxiv.org/abs/2404.13076)).
- 이 손실은 작은 평가로는 드러나지 않습니다. 독립 검증의 가치는 생성자와 검증자가 같이 틀리지 않는 데 있고, 그 차이는 드물게 나오는 꼬리 케이스에서만 보입니다. 골든 예제 10개에서 점수가 같다고 해서 차이가 없는 것은 아닙니다. 글이 직접 든 사례에서도 깨진 과제는 두 번 중 한 번만 실패했습니다.
- 그래서 입증 책임을 뒤집습니다. 용량 경계는 "남길 근거"가 필요하지만, 독립성 경계는 "합칠 근거"가 필요합니다.

**신뢰 경계**

- 비공개 데이터 접근, 신뢰할 수 없는 콘텐츠, 외부로 내보낼 수단을 한 에이전트가 모두 가지면 프롬프트 인젝션으로 데이터가 새는 경로가 생깁니다([Willison, The lethal trifecta](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). 신뢰할 수 없는 입력을 읽는 쪽을 쓰기·전송 도구가 없는 서브에이전트로 떼어 내면 이 조합을 깰 수 있습니다.
- 단, 반환을 자유 텍스트가 아니라 필드와 형식이 정해진 데이터로 제한해야 효과가 있습니다. 자유 텍스트 요약은 주입된 지시를 메인 에이전트로 그대로 옮길 수 있습니다.
- 이것은 보안 속성이라 품질 평가로는 측정되지 않습니다. 골든 예제에는 공격이 들어 있지 않습니다.

### 4.3 글의 원칙을 경계에 적용하기

글은 규칙을 두 가지로 나눴습니다. 상황에 따라 조정하는 절차는 스킬로, 깨지면 안 되는 제약은 도구로 둡니다. 같은 구분을 경계에 적용하면 이렇게 됩니다.

| 구분 | 규칙 (글) | 경계 (보완) |
| --- | --- | --- |
| 조정 대상 (소프트) | 스킬: 평가로 개선 | 용량 경계: 평가로 합치거나 나눔 |
| 고정 대상 (하드) | 도구 속 제약: 평가와 상관없이 강제 | 독립성·신뢰 경계: 평가와 상관없이 유지 |

**글이 규칙에는 적용한 원칙을 아키텍처 경계에는 적용하지 않았다**는 것이 이 보완의 요지입니다. 결론을 뒤집지는 않고, "측정으로 정하는 경계"와 "원칙으로 고정하는 경계"를 구분하라는 단서가 붙습니다.

## 5. 보완 3: 고객 응대 에이전트와 코딩 에이전트

### 5.1 중요한 지표가 다릅니다

글의 사례는 대부분 고객 응대용이라 지연과 브랜드 어조가 핵심 지표입니다. 코딩 에이전트는 작업이 몇 시간씩 이어지고, 지연보다 정확성과 컨텍스트 오염이 중요합니다. 컨텍스트가 서서히 오염되는 저하는 "측정 가능한 저하"로 잘 잡히지 않습니다.

### 5.2 SDD에서는 스펙이 인수인계서입니다

- 리뷰를 거친 스펙은 LLM이 쓴 요약보다 손실이 훨씬 적은 핸드오프 계약입니다. 그래서 SDD에서는 태스크를 새 컨텍스트로 나눠 실행하는 비용이 글의 사례보다 작습니다.
- 다만 구현하면서 알게 된 사실은 스펙에 남지 않습니다. "이 클래스는 이런 버릇이 있더라" 같은 발견입니다.
- 그래서 기준은 **"task N을 하면서 알게 된 것이 task N+1에 얼마나 필요한가"**입니다. 많이 필요하면 합치고, 스펙만으로 충분하면 나눠도 됩니다. 기존 원칙인 "중간 관찰이 다음 결정을 바꾸는 작업은 위임하지 않는다"를 태스크 사이로 넓힌 것이고, 글의 "강하게 결합된 전문 에이전트는 합쳐라"와도 같은 기준입니다.

## 6. 페르소나 기반 멀티 에이전트 회고

한때 에이전트를 조직도처럼 구성하고 페르소나를 입히는 멀티 에이전트 워크플로우가 당연한 것처럼 이야기됐습니다. 이 프로젝트의 입장은 "멀티 에이전트는 필요에 의해서만 분리한다"였고, 이 글이 그 입장을 뒷받침합니다.

### 6.1 당시에는 모델의 약점을 메우는 우회책이었습니다

당시 모델은 긴 지시를 잘 따르지 못하고 컨텍스트도 작아서, 역할을 좁게 쪼개 프롬프트를 단순하게 만드는 것이 약점을 메우는 방법이었습니다. 모델이 좋아지면서 그 이유가 사라졌습니다.

그래서 **"필요"는 모델 성능에 따라 계속 바뀝니다.** 지금 필요한 분리가 내년에는 불필요해질 수 있고, 작업이 길어지면 새로운 분리가 필요해질 수도 있습니다. 글도 모델이 좋아질수록 맞는 구조가 계속 바뀐다고 말합니다.

### 6.2 사람 조직의 분업 이유 중 무엇이 옮겨오는가

| 사람이 분업하는 이유 | 에이전트에서 | 대응 수단 |
| --- | --- | --- |
| 전문성을 쌓는 데 몇 년이 걸림 | 옮겨오지 않음. 모두 같은 모델 | 스킬로 즉시 로드 |
| 한 사람이 담을 수 있는 양이 한정됨 | 옮겨옴 | 용량 경계 |
| 몸이 하나라 동시에 여러 일을 못 함 | 옮겨옴 | 병렬 서브에이전트 |
| 직무 분리 (작성자 ≠ 승인자, 독립 감사) | 옮겨옴 | 독립성·신뢰 경계 |

위 세 줄은 효율을 위한 분업이고, 마지막 줄은 통제를 위한 분업입니다. 효율을 위한 분업 중에서는 용량과 병렬성만 옮겨오고, 페르소나가 흉내 내던 전문성 분업은 옮겨오지 않습니다. 통제를 위한 분업은 그대로 옮겨옵니다.

### 6.3 페르소나에서 남길 만한 것

페르소나에 쓸모 있는 부분이 있었다면 역할 이름이 아니라 **다른 목적과 다른 정보**입니다. 반박만 하는 리뷰어나 구현 과정을 모르는 검증자는 정당합니다. "10년 차 시니어 아키텍트" 같은 설정은 아무것도 더하지 않습니다.

## 7. 정리: 서브에이전트 분리 판단 기준

### 7.1 기본값

단일 루프 + 스킬(절차) + 도구·훅(하드 제약). 나누지 않는 것이 기본입니다.

### 7.2 판단 순서

| 순서 | 질문 | 예이면 | 판단 방법 |
| --- | --- | --- | --- |
| 1 | 신뢰할 수 없는 입력을 읽는 에이전트에 쓰기·전송 수단이 함께 있는가 | 분리 | 원칙 (평가하지 않음) |
| 2 | 생성자의 추론을 모르는 판단이 필요한가 | 분리 | 원칙 (합치려면 근거 필요) |
| 3 | 독립적인 일을 병렬로 돌리고 결과만 받으면 되는가 | 분리 검토 | 처리량·비용 측정 |
| 4 | 단일 루프에서 컨텍스트 비대화로 인한 저하가 측정되는가 | 분리 검토 | 평가 (글의 기준) |
| – | 위에 해당하지 않음 | 단일 루프 유지 | – |

앞의 둘은 평가 결과로 뒤집을 수 없는 원칙이고, 뒤의 둘은 측정 결과에 따라 바뀝니다. 그래서 원칙을 먼저 묻습니다.

### 7.3 나누는 이유가 되지 않는 것

| 흔한 분리 이유 | 대신 쓸 수단 |
| --- | --- |
| 역할·페르소나 (PM, 아키텍트, 개발자, QA) | 스킬 |
| 팀 소유 | 스킬·도구·평가의 소유권(DRI) |
| 문제 유형 라벨 | 스킬, 의도 단위로 묶은 도구 |
| 절차 표준화 | 스킬 |

### 7.4 나눌 때의 계약

- 서브에이전트는 도구처럼 호출하고, 반환은 자유 텍스트가 아니라 스키마가 정해진 아티팩트로 받습니다. 메인 에이전트는 그 결과를 실제 데이터(git diff, 테스트 결과 XML 등)와 대조합니다. 서브에이전트 성공 오보고 문제의 해결 방향과 같습니다.
- 신뢰 경계의 반환은 특히 필드와 형식을 좁힙니다(4.2절).
- 완전한 핸드오프는 서브에이전트가 사용자와 직접 대화해야 할 때만 씁니다(글의 권고).

### 7.5 평가 방법

- 합칠 때는 한 번에 하나씩 바꾸고 전후를 비교합니다(글의 권고).
- 1회 통과율(pass@1)이 아니라 k회 모두 통과하는 비율(pass^k)을 봅니다. τ-bench에서 gpt-4o는 retail 도메인의 pass^1이 약 61%였지만 pass^8은 25% 미만이었습니다. 한 번 성공하는 것과 일관되게 성공하는 것은 다릅니다([Yao et al., 2024](https://arxiv.org/abs/2406.12045)).
- 총점이 아니라 과제별로 결과가 뒤바뀐 것을 봅니다. 리팩토링 전에 특성 테스트(characterization test)를 깔아 두는 것과 같은 원리입니다.

### 7.6 기존 위임 기준의 수정 (제안)

| 기존 기준 | 수정 제안 | 이유 |
| --- | --- | --- |
| ① 컨텍스트 격리가 필요한가 | 용량·독립성·신뢰로 나누고, 판단 방법을 다르게 둠 | 세 경계는 입증 책임이 다름 (4장) |
| ② 절차 표준화가 필요한가 | 서브에이전트 기준에서 빼고, 스킬을 만들 이유로 옮김 | 스킬과 서브에이전트를 직교 축으로 운용한다는 기존 결정과 맞음. 절차는 분리할 이유가 아니라 분리된 에이전트에 실어 보내는 내용 |

## 8. 기존 문서에 미치는 영향

- [에이전트 코드 리뷰 제안](2026-11-agent-code-review-stage.md)의 결론(별도 컨텍스트에서 읽기만 하는 리뷰어)은 그대로이고, 근거만 다시 정리됩니다. 리뷰어를 나누는 이유는 독립성 경계입니다. 6.1절이 기준 ②(절차 표준화)를 분리 근거로 든 부분은, 분리된 리뷰어에 체크 항목과 출력 스키마를 고정하는 이유로 읽는 것이 맞습니다.
- 같은 문서 7장의 채택률 측정은 "어떤 항목을 차단 게이트로 올릴지"를 정하는 것이지, "리뷰어를 메인 에이전트에 합칠지"를 정하는 것이 아닙니다. 독립성 경계는 측정 결과와 상관없이 유지합니다.

## 9. 열린 질문

| 질문 | 현재 생각 |
| --- | --- |
| 독립성 경계에서 리뷰어에게 무엇을 숨길 것인가. 스펙은 주고 구현 과정만 숨길지, 스펙도 숨기고 코드만 보게 해서 "스펙 없이도 의도가 읽히는가"까지 검증할지 | 스펙을 주는 쪽을 제안함 (미합의). 리뷰 항목 대부분(TR-1, FR-1, FR-4)이 스펙 정합성을 보므로 스펙 없이는 판단 기준이 없음. "의도가 읽히는가"는 별도 점검으로 나눌 수 있음 |
| Kiro 워크플로우의 각 단계(task 실행, 코드 탐색, 리뷰)를 세 경계 중 어디에 둘 것인가 | 미정 |
| 코딩 에이전트에서 용량 경계의 "측정 가능한 저하"를 어떻게 관찰할 것인가 | 미정. 후보: 같은 feature를 단일 루프와 태스크별 분리로 각각 실행해 리뷰 findings 수와 재작업 횟수를 비교 |

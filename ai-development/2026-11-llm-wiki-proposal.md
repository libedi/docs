# 도메인·설계 맥락을 축적하는 LLM Wiki 도입 제안

작성일 2026-11-12  
상태 사내 조사 및 적용 검증용 제안  
대상 Kiro에서 브레인스토밍 스킬과 feature/module 스펙을 운영하는 개발팀

환경 전제는 Windows 11·Git Bash, 폐쇄망, 워크트리 병렬 작업이다. 추가 도구는 사내 Nexus를 통한 npm 배포와 설치 후 외부 바이너리 다운로드 여부를 확인한다. Python/PyPI 의존성은 현 환경에서 사용하기 어렵다. codegraph는 사용 가능한 팀원의 코드 탐색을 지원하며, 적용 시 IDE·CLI별 실제 스킬 연결과 설치 상태를 확인한다.

## 1. 도입 배경과 목표

팀은 요건에 대한 브레인스토밍을 수행하고, 스펙 작성에 충분한 요건이 확정되었다는 게이트를 통과하면 Kiro spec workflow로 진행한다. 개발 중에는 feature 스펙을 작성하며, 개발 완료 후 module 스펙으로 승격할 내용을 검토해 갱신한다. module 스펙에는 모듈의 목적, 스코프, 설계 결정, 크로스컷팅 계약, 대체된(superseded) 결정 등이 담긴다.

이 구조에서도 새로운 세션을 시작할 때 여러 AS-IS·TO-BE 분석과 도메인 문서의 맥락을 에이전트에게 다시 설명하는 비용이 발생한다. 작성자도 여러 문서에 흩어진 내용의 의존성이나 영향을 모두 발견하기 어렵다.

LLM Wiki의 목표는 최초 진입 시 에이전트가 도메인·설계·구조의 맥락을 확보하고, 그 이해를 바탕으로 브레인스토밍의 질문과 검토 방향을 잡도록 돕는 것이다. 관련 지식을 종합한 결과를 보존해 다음 세션에서 재사용한다.

효과는 아직 사내 문서로 검증하지 않았다. 이 문서는 대화에서 확인된 워크플로우를 바탕으로 한 적용안이며, 실제 문서 내용과 스킬 구현을 조사해 조정해야 한다.

## 2. 아이디어의 출처와 이번 제안

카파시의 LLM Wiki는 원문, LLM이 작성하는 연결된 Markdown 위키, 운영 규칙을 정의하는 스키마로 구성된다. 자료를 반영하는 ingest, 질문과 탐색 결과를 축적하는 query, 모순과 누락된 연결 등을 점검하는 lint를 제시한다. index.md는 탐색을 돕고 log.md는 작업 이력을 기록한다.

이번 제안은 이 패턴을 팀의 브레인스토밍과 feature/module 스펙 운영에 연결한다. 아래의 문서 책임, 디렉터리 구조, 갱신 시점, 평가 방법은 팀 상황에 맞춘 제안이다.

원안은 raw sources를 불변 자료로 취급한다. 이번 제안의 분석·feature/module 스펙은 기존 개발 절차에 따라 변경되므로, 읽은 내용의 버전과 변경 영향을 추적한다.

## 3. 문서별 책임과 근거

| 문서 | 책임 | 위키와의 관계 |
| --- | --- | --- |
| 분석·업무·온보딩 원문 | 조사 결과, 업무 지식, 관찰, 제안과 배경 | 원문 내용과 적용 조건을 종합하는 입력 |
| feature 스펙 | 이번 변경의 요건, 설계, 구현·검증 범위 | 변경의 상세 근거와 배경 |
| module 스펙 | 모듈의 목적·스코프, 결정, 계약과 대체 이력 | 현재 적용할 모듈 계약과 결정의 기준 |
| LLM 위키 | 도메인 지식, 전체 구조, 여러 내용의 관계와 미결 질문 | 최초 진입과 탐색, 브레인스토밍을 지원 |

위키는 module 스펙의 상세 계약을 참조하고, 이해에 필요한 요약과 다른 지식과의 관계를 설명한다. 계약과 결정 이력의 상세 관리는 module 스펙에 둔다.

관계의 단위는 문서 안의 사실, 정의, 전제, 제안, 결정이다. 관계는 한 모듈 안에서도, 여러 도메인과 모듈 사이에서도 나타날 수 있다. 관련 페이지 링크와 함께 무엇이 어떤 조건에서 연결되는지 문장으로 설명한다.

위키 설명이 module 스펙과 충돌하면 해당 스펙의 적용 범위와 대체 여부를 확인한다. 코드와 스펙이 어긋난 경우에는 의도한 계약과 관찰된 구현을 각각 근거와 함께 기록하고 확인할 문제로 남긴다. 최근 작성일만으로 어느 설명이 유효한지 확정하지 않는다.

## 4. 문서 구조 제안

사내 프로젝트의 docs/wiki/에는 현재 onboarding/, work/, 요금안내정보관리/ 등이 있다. 원문 문서는 목적과 도메인에 맞춰 정리하고, LLM이 종합하는 영역을 docs/wiki/llm/에 둔다.

아래 표는 정리 후 목표 구조다. 원문 이동이 완료되기 전에는 실제 현재 경로를 근거 표와 링크에 사용한다. 예를 들어 요금안내정보관리 원문의 현재 경로는 `docs/wiki/요금안내정보관리/`이며, `docs/wiki/domains/요금안내정보관리/`는 재배치 후 제안 경로다. `llm/` 아래 항목은 새로 구성할 영역이다.

| 정리 후 제안 경로 | 역할 |
| --- | --- |
| docs/wiki/README.md | 전체 문서 안내와 LLM 위키 진입점 |
| docs/wiki/onboarding/ | 프로젝트 소개, 개발 환경과 신규 참여자 안내 |
| docs/wiki/domains/요금안내정보관리/ | 업무 설명, 규칙, AS-IS·TO-BE 분석 |
| docs/wiki/work/ | 도메인 공통 작업 방법과 절차 |
| docs/wiki/llm/index.md | 주제별 안내와 탐색 경로 |
| docs/wiki/llm/overview.md | 전체 업무 흐름, 도메인·모듈 구조와 주요 연결 |
| docs/wiki/llm/topics/ | 주제별 종합, 내용 간 관계, 미결 질문 |
| 각 주제 페이지의 근거 표 | 원문 경로·절, 반영한 blob ID, 검토 상태 |
| docs/wiki/llm/maintenance.md | 작성·참조·갱신 규칙 |
| docs/wiki/llm/log/ | 작업별 반영·검토 기록. 날짜와 feature/작업 식별자로 파일 구분 |

경로는 적용안이다. work/의 실제 내용과 기존 링크를 조사해 이동 대상을 정한다. 파일 이동 시 본문 링크와 스킬의 경로 참조도 함께 수정한다. 원문 정리는 별도 변경 단위로 진행하며, 사용 중인 워크트리의 경로 참조와 병합 시점을 확인한다. 시범 위키는 현재 경로로 시작할 수 있다. 효과 비교에서는 양쪽에 동일한 정리 상태와 버전의 원문을 제공한다.

feature/module 스펙은 기존 경로에서 관리하며 각 주제 페이지의 근거 표에서 연결한다. topics/의 페이지는 업무 개념과 질문을 중심으로 구성한다. 하나의 원문은 여러 주제에 기여하고, 하나의 주제는 여러 원문을 종합할 수 있다.

index.md는 어디에 무엇이 있는지 안내한다. overview.md는 최초 진입에 필요한 전체 맥락을 설명한다. 상세한 관계와 근거는 주제 페이지에 둔다. 문서가 늘어나면 실제 탐색 필요에 맞춰 topics/를 도메인별로 나눈다.

## 5. 주제 페이지 작성 기준

페이지에는 현재 이해한 내용, 적용 범위, 다른 내용과의 관계, 근거, 필요한 미결 질문을 담는다. 내용이 부족한 항목은 억지로 채우지 않는다.

| 검토 관점 | 확인할 질문 |
| --- | --- |
| 동일한 개념 | 서로 다른 표현이 같은 업무나 데이터를 뜻하는가? |
| 전제와 의존 | 이 결정이 성립하려면 다른 내용의 어떤 조건이 필요한가? |
| 영향 | 이 조건이 바뀌면 다른 동작이나 설계에 무엇이 달라지는가? |
| 일치와 충돌 | 같은 시점·범위·조건에서 설명이 일치하는가? |
| 보완 | 한 문서의 예외나 제약이 다른 설명을 구체화하는가? |
| 누락 | 함께 적용할 때 정해지지 않은 동작이나 책임이 생기는가? |

중복된 정의는 적용 범위가 같은지 확인한 뒤 종합하고 출처들을 연결한다. 원문의 예외 조건과 시점은 함께 보존한다. 업무상 확인된 사실, 검토 중인 제안, 승인된 결정, 에이전트가 도출한 추론이 드러나도록 작성한다.

관계에 필요한 양쪽 근거를 해당 절까지 연결한다. 추론에는 도출 이유와 확인할 조건을 적는다. 다른 위키 페이지를 참조하더라도 원래의 분석 또는 스펙으로 추적할 수 있게 한다.

전체 위키는 계속 관리하는 지식 문서다. 개별 내용의 확정 정도와 구현 상태를 표시한다. 스펙 승인, 구현 검증, 운영 반영은 서로 다른 시점으로 취급한다.

## 6. 작은 예시

다음 내용은 설명을 위한 가상 업무 규칙이다.

| 원문 | 내용 |
| --- | --- |
| A. 청구 대상 분석 | 한 청구 계정에 여러 회선이 연결된다. 청구 대상은 마감 시점에 확정한다. |
| B. 청구 파일 분석 | 계정별 레코드를 만들고 회선 요금을 합산한다. |
| C. 재처리 분석 | 한 계정에 여러 회선이 연결된다. 실패 계정을 재처리하며 최신 회선 정보를 조회하는 방안을 검토한다. |

청구계정 페이지는 A와 C의 중복 정의를 한 번 설명하고 두 출처를 연결한다. B를 함께 읽어 회선 구성과 레코드의 합산 대상이 연결됨을 설명한다.

재처리 페이지에는 다음 종합을 남긴다.

> 마감 후 회선 구성이 바뀔 수 있다면 최신 정보를 조회하는 재처리는 최초 처리와 합산 대상이 달라질 수 있다. 이는 A의 마감 규칙, B의 합산 규칙, C의 재조회 제안을 종합한 추론이다. 마감 시 계정 목록과 회선 구성 중 어디까지 확정하는지, 마감 후 회선 변경이 가능한지 확인해야 한다.

이후 module 스펙에 마감 당시 대상 재사용이 계약으로 확정되면, 위키는 그 계약을 근거로 재처리 설명을 갱신한다. 상세한 결정과 대체 이력은 해당 module 스펙으로 연결한다.

새 브레인스토밍 세션은 이 페이지를 읽고 재처리의 시간 기준을 질문할 수 있다. 사용자가 A, B, C의 연결을 다시 설명하는 부담을 줄이는 것이 목표다.

## 7. 브레인스토밍과 Kiro 스펙 연결

| 시점 | 수행할 일 |
| --- | --- |
| 브레인스토밍 시작 | index와 overview로 범위와 전체 맥락을 파악하고 관련 주제와 module 스펙을 읽는다. |
| 브레인스토밍 진행 | 전제·영향·미결 질문을 논의에 반영하고, 중요한 판단은 원문으로 확인한다. |
| 기존 요건 확정 게이트 통과 | 확정 요건, 적용 범위, 판단 근거와 관련 페이지를 스펙 단계에 전달한다. |
| Kiro 스펙 시작 | 확정 요건과 현재 module 계약을 기준으로 관련 위키 맥락을 이어받는다. |
| feature 개발 완료 | 기존 module 스펙 승격 검토·갱신 후 위키 영향 여부를 검토하고 필요한 페이지를 갱신한다. |

요건이 충분히 확정됐는지 판단하는 책임은 기존 브레인스토밍 스킬의 게이트에 둔다. 승인된 스펙 변경이 필요한 질문은 기존 변경·승인 절차로 연결한다.

module 스펙 승격 사항이 없어도 도메인 용어가 명확해지거나 미결 질문이 해결됐다면 위키를 갱신할 수 있다. 갱신 필요 여부와 근거를 기존 완료 보고에 짧게 포함한다.

위키 변경은 해당 feature MR에 포함해 기존 리뷰 시점에 사실·추론·적용 범위와 근거를 검토하는 방식을 기본안으로 한다. 독립적인 위키 정리도 문서 MR로 검토한다. 사내의 실제 리뷰 절차에 맞춰 연결한다.

실제 스킬과 steering의 파일명, 로딩 방식, 완료 절차를 조사해 연결 지점을 정한다. 읽기 진입 안내는 브레인스토밍·스펙 시작 지침에, 작성 규칙은 maintenance.md에 두는 구성을 우선 검토한다.

## 8. 최초 진입과 탐색 범위

탐색과 링크 검증의 기준은 현재 작업 중인 워크트리 루트다. 하위 .worktrees/ 사본은 탐색에서 제외하며, 경로가 같은 다른 브랜치 문서를 섞지 않는다. codegraph를 사용하면 projectPath도 해당 루트로 지정한다.

에이전트는 index와 overview를 읽어 전체 구조를 잡고, 이번 요건과 관련된 주제로 내려간다. 직접 관련된 계약을 이해하는 데 필요한 다른 주제도 따라간다. 중요한 구현 판단에는 해당 module 스펙과 원문을 확인한다.

초기 위키가 일부 문서만 반영했다면 index에 반영 범위와 미반영 영역을 명시한다. 위키에 내용이 없는 주제는 원문과 스펙에서 추가 탐색한다. 검색 결과가 없다는 사실을 관계가 없다는 판단의 근거로 삼지 않는다.

overview는 전체 흐름을 이해하는 데 필요한 크기로 유지한다. 상세 내용은 주제 페이지로 연결한다. 팀이 실제로 사용하는 용어와 동의어를 안내에 넣어 명칭 차이로 인한 누락을 줄인다.

overview는 초기 운영 목표로 본문 약 100줄 이내를 검토한다. 이를 초과하면 상세 설명을 주제로 옮길지 판단하고 실제 진입 비용에 따라 조정한다.

위키는 이해에 필요한 모듈 책임과 구조 요약도 담는다. 최신 호출 관계와 구현의 상세 확인에는 사용 가능한 codegraph 또는 파일 검색·읽기를 활용한다. 코드에서 유도 가능한 정보라도 도메인 설명에 필요하면 근거와 함께 요약한다. 사내 codegraph 라우팅 규칙 R5에 도메인·설계 맥락 질문은 위키 진입점과 module 스펙으로 안내하는 행을 추가할지 검토한다.

## 9. 갱신과 추적

각 주제 페이지에 저장소 루트 기준 원문 경로, 절, 반영한 Git blob ID, 검토 상태를 표로 기록한다. overview가 원문을 직접 종합하면 같은 근거 표를 둔다. 이 정보는 검토 후 갱신한다.

커밋된 원문은 `git rev-parse "HEAD:<path>"`로 blob ID를 확인한다. 작업 트리의 변경 내용을 읽었다면 `git hash-object --path="<path>" -- "<path>"`로 그 내용의 ID를 계산하고, 커밋 전 최종 원문과 일치하는지 확인한다. Windows 줄바꿈과 저장소 필터를 반영하는 동일한 방식으로 비교한다. 커밋 ID가 바뀌어도 내용이 같으면 blob ID를 내용 식별에 사용할 수 있다.

근거 표를 포함한 변경을 커밋할 때는 반영한 원문 내용도 해당 커밋 또는 보존된 이전 커밋에 포함되도록 한다. 작업 중 계산한 임시 ID는 원문을 수정했다면 다시 확인한다.

해시 차이는 근거 파일이 변경됐다는 재검토 신호다. 해당 주장의 유효성은 변경된 절과 조건을 읽어 판단한다. 파일이 이동되면 경로도 갱신한다. ID 자체는 과거 내용의 영구 보존을 보장하지 않으므로 원문 이력은 Git의 보존된 이력으로 추적한다.

이전 blob과 현재 커밋된 원문을 읽을 수 있으면 `git diff <기록한-blob-ID> "HEAD:<path>"`로 변경 부분을 먼저 확인한다. 근거 표의 해당 절과 그 절에 적용되는 공통 정의·전제의 변경을 확인해 재검토 범위를 좁힌다. 작업 트리에 미커밋 변경이 있으면 그 변경도 함께 검토한다. 이전 blob을 읽을 수 없거나 관계에 미치는 영향이 불명확하면 현재 원문의 관련 절과 전제를 다시 읽는다. 재검토 후 영향 유무와 판단 근거를 기록하고 근거 표의 버전을 갱신한다.

명령의 기준 — [git rev-parse](https://git-scm.com/docs/git-rev-parse), [git hash-object](https://git-scm.com/docs/git-hash-object), [git diff](https://git-scm.com/docs/git-diff).

1. 추가·수정·이동·삭제된 원문을 파악한다.
2. 해당 내용을 근거로 사용하는 페이지를 찾는다.
3. 변경된 설명과 그 설명에서 도출한 관계·추론을 재검토한다.
4. 영향이 이어지는 주제와 index·overview를 필요한 범위에서 갱신한다.
5. 실제로 검토한 원문 기준과 결과를 기록한다.

원문 삭제나 근거 소실 시 해당 설명의 유효성을 다시 판단한다. 검토가 완료되지 않은 페이지는 갱신 필요 상태를 표시하고 남은 범위를 기록한다. 기존 문서 사이에서 새 관계가 발견되면 질문·분석 결과도 위키에 반영할 수 있다.

근거 표를 주제별로 두고 log/의 기록을 작업별 파일로 나눠 공통 파일 수정 집중을 줄인다. index는 주제 추가·이동·삭제 또는 안내 변경 시에 갱신한다. 전체 원문 목록이 필요해지면 주제별 근거 표에서 생성하는 방식을 검토한다.

텍스트 충돌이 나면 양쪽 변경을 확인해 해결한다. 자동 병합에 성공한 경우에도 최신 module 계약과 원문에 비춰 의미상 충돌을 검토한다. 변경 이력은 Git으로 관리하고 작업별 log에는 검토 범위와 남은 항목을 적는다.

### 9.1. Lint

갱신한 페이지는 완료 전 점검하고, 시범 적용 종료 시 전체 위키를 점검한다. 운영 중 전체 점검 주기는 문서 증가와 변경 빈도를 보고 정한다.

- 기계 점검은 근거 파일 존재, blob ID 차이, 내부 링크·절의 유효성, index에서 도달할 수 없는 주제 후보를 확인한다.
- 에이전트는 모순, 대체된 주장, 누락된 관계, 근거 없는 추론, 동일 개념의 중복·불일치를 원문과 비교한다.
- 점검 결과에는 확인 범위와 확인 불가능한 링크를 표시한다. 기계 검사 통과만으로 의미의 일관성을 확정하지 않는다.

시범 단계에서 Git Bash 또는 기존 Node 환경으로 점검 도구를 구현할지 판단한다. 자동화할 때는 지원할 Markdown 링크·앵커 형식을 명시하고, 검사 범위 밖 구문은 미검증으로 보고한다. 반복 점검 비용을 확인하며 도구를 추가한다.

## 10. 사내 에이전트 적용 순서

| 단계 | 작업 | 산출물 |
| --- | --- | --- |
| 현황 조사 | 문서, feature/module 스펙, 브레인스토밍 스킬, 완료 절차, 기존 경로 참조 확인 | 문서 목록과 연결 지점 |
| 구조 정리안 | onboarding/work/도메인 문서의 역할과 이동 필요성 검토 | 기존 경로와 제안 경로의 대응 |
| 범위 선정 | 실제 다음 브레인스토밍에서 사용할 주제와 관련 원문 선정 | 원문 목록과 초기 반영 범위 |
| 시범 구성 | index, overview, 주제별 근거 표, 작업별 기록과 운영 규칙 구성 | 근거를 추적할 수 있는 위키와 연결 지침 |
| 진입 검증 | 새 세션에서 개발 목표와 위키 진입점으로 브레인스토밍 | 복원한 맥락과 발견한 질문 |
| 갱신 검증 | 실제 feature 완료 또는 원문 변경을 반영 | 설명·관계·미결 질문 갱신 결과 |
| Lint 검증 | 파일·링크·해시 및 모순·누락 관계 점검 | 점검 범위, 발견 사항, 자동화 필요성 |
| 적용 조정 | 결과를 검토해 문서와 스킬 연결 개선 | 팀에 맞춘 운영 방식 |

초기에는 기존 Markdown·Git·에이전트의 파일 탐색으로 시작한다. 별도 검색 도구나 자동화는 실제 규모와 반복 비용을 확인해 판단한다.

## 11. 효과 검증

검증할 가설은 최초 진입에서 도메인·설계·구조의 맥락을 확보하면 브레인스토밍의 질문과 검토 방향이 개선된다는 것이다.

같은 개발 목표에 대해, 기존 문서 인덱스와 원문·스펙을 제공하는 방식과 여기에 종합 위키를 추가한 방식을 새 세션에서 비교한다. 양쪽 모두 같은 근거에 접근할 수 있게 하고 같은 과제와 검토 기준을 사용한다.

| 관찰 항목 | 확인 방법 |
| --- | --- |
| 최초 맥락 이해 | 주요 용어, 구조, 계약과 적용 범위를 정확히 설명하는지 확인 |
| 반복 설명 부담 | 사용자가 다시 설명해야 했던 배경과 관계를 기록 |
| 질문의 유용성 | 요건 확정에 필요한 전제·예외·모듈 간 영향을 짚었는지 검토 |
| 근거의 정확성 | 제시한 관계가 원문으로 뒷받침되는지, 추론이 표시됐는지 확인 |
| 갱신의 유효성 | 원문 변경 후 오래된 설명과 파생 관계가 수정되는지 확인 |
| 운영 비용 | 위키 작성·검토·갱신 비용과 다음 작업에서 절약한 설명 비용 비교 |

한 번의 응답만으로 효과를 확정하기 어렵다. 실제 작업에서 반복 설명이 줄고 유용한 관계가 재사용되는지 관찰한다. 평가 결과에 따라 페이지 범위와 갱신 방식을 조정한다.

## 12. 적용 시 확정할 사항

제안서 작성에 필요한 방향은 정리되었다. 다음 항목은 사내 에이전트가 실제 환경을 조사하며 확정한다.

- 기존 work/ 문서의 성격과 이동할 경로, 수정할 링크.
- feature/module 스펙의 실제 위치와 현재 결정 식별 방식.
- 브레인스토밍 시작과 개발 완료에 지침을 연결할 파일.
- codegraph 라우팅 규칙 R5에 위키 진입 안내 행을 추가할지 여부.
- 초기 위키가 다룰 주제와 미반영 영역의 표시.
- blob ID 기록·비교 방식의 사내 Git 필터 호환성과 변경 영향 검토 범위.
- 위키 변경을 기존 feature·문서 MR 리뷰에 포함할 구체적 시점.

위키의 가치 판단은 기존 스펙의 존재와 함께, 여러 스펙과 분석의 내용을 종합한 맥락이 최초 진입과 다음 논의에서 얼마나 재사용되는지를 기준으로 한다.

## 13. 사내 적용 지침 초안

다음 문구는 기존 스킬과 완료 절차에 맞춰 편집할 수 있는 초안이다.

### 브레인스토밍 진입

> 현재 워크트리의 docs/wiki/llm/index.md와 overview.md를 읽고 반영 범위를 확인한다. 이번 요건과 관련된 주제와 module 스펙을 찾아 도메인 개념, 전제, 모듈 간 영향을 파악한다. 미결 질문과 근거 변경 여부를 확인해 브레인스토밍에 반영한다. 위키에서 다루지 않은 부분은 원문을 탐색한다. 확정한 요건과 적용 범위, 판단 근거를 기존 게이트를 통해 스펙 단계에 전달한다.

이 안내는 브레인스토밍 스킬이 실행될 때 읽도록 배치한다. 스펙 시작 지침에도 관련 맥락을 이어받는 안내를 연결한다.

### 개발 완료

> 기존 feature 완료 및 module 스펙 승격 검토를 수행한 뒤 관련 위키의 설명·관계·미결 질문에 미치는 영향을 확인한다. 필요한 페이지와 근거 표를 갱신하고 변경 범위를 lint한다. 갱신 여부와 남은 사항을 완료 보고에 포함하고 위키 변경을 해당 feature MR의 리뷰 대상으로 포함한다.

### maintenance.md에 반영할 규칙

> 현재 워크트리의 원문과 스펙을 근거로 주제별 설명을 종합한다. 사실·제안·결정·추론과 적용 시점을 드러내고 관계의 양쪽 근거를 연결한다. 원문 변경 시 근거 표를 조회해 영향받는 주장과 파생 관계를 재검토한다. 검토한 내용의 blob ID를 기록하고 미완료 검토 범위를 표시한다. index는 탐색 구조 변경 시 수정하며 반영 기록은 log/의 작업별 파일에 둔다. 파일·링크·버전 점검과 의미상 모순·누락 점검을 수행한다. 계약 변경은 기존 스펙 절차로 연결하고 위키 변경은 기존 MR 리뷰에 포함한다.

## TL;DR

- **두 출처 모두 추가보다 삭제를 더 많이 권합니다.** 이전 모델의 약점을 메우려고 넣었던 문구("신중히 생각해", "멈추지 말고 계속해", 대문자 강조)는 이제 효과가 없거나 과잉 행동을 부릅니다. 새 규칙을 넣기 전에 기존 steering·스킬을 먼저 감사합니다.
- **지시는 모델이 판단하는 것과 하네스가 강제하는 것으로 나뉩니다.** 모델이 읽고 판단하는 지시(steering, 스킬, 프롬프트)는 대부분 지켜지지만 보장되지 않습니다. 하네스가 강제하는 장치(권한 규칙, pre-commit 훅, CI, MR 승인)는 모델의 판단과 무관하게 적용됩니다. 예외가 없어야 하는 규칙만 후자로 옮기고, 그 수는 적게 유지합니다.
- **검증 수단과 강제 수단은 다릅니다.** 테스트와 검증 스크립트는 검사 자체는 기계적이지만, 모델이 실행 여부를 정한다면 실행은 보장되지 않습니다. 실패하거나 실행되지 않았을 때 완료나 병합을 막는 장치가 있어야 강제입니다.
- **steering에는 코드를 읽어도 알 수 없는 것만 남깁니다.** 검증 명령, 코드가 오해를 부르는 지점, 레포에 없는 결정, 두 번 이상 교정한 것입니다.
- **텍스트 보고는 완료의 증거가 아닙니다.** 완료는 pass/fail로 돌아오는 검사와 그 실행 출력으로 판정합니다. 서브에이전트 성공 오보고 문제의 처방도 같습니다.
- **모델에게 판단을 맡기는 범위는 검사의 신뢰도만큼만 넓힙니다.** As-Is 대사가 불가능한 마이그레이션에서는 AC와 속성(jqwik)의 정확성이 유일한 안전망입니다. 과정 지시를 줄여 아낀 노력은 AC 확정 단계로 옮깁니다.
- **API 파라미터(effort, max_tokens, thinking 표시, refusal fallback)는 Kiro가 쥐고 있습니다.** 이 문서는 확인 항목으로만 다룹니다.

## 이 문서를 받은 에이전트에게

이 문서는 사내 Kiro 하네스(steering, 스킬, 커스텀 에이전트, 훅, 검증 스크립트)를 개선하기 위한 판정 기준입니다. 다음 순서로 사용합니다.

1. 1~7장의 기준을 읽습니다.
2. 프로젝트의 steering, 스킬, 커스텀 에이전트 정의, 훅, 검증 스크립트를 전부 읽고 기준에 대조합니다.
3. 결과를 [9장 적용 후보 목록](#9-적용-후보-목록)의 표에 채웁니다. 항목마다 파일 경로와 줄 번호를 근거로 적습니다.
4. **표를 채우는 것까지만 합니다.** 실제 파일 변경은 사람이 항목별로 승인한 뒤에 진행합니다.
5. 기준을 적용하기 애매한 항목은 버리지 말고 "판단 필요"로 표시해 남깁니다.
6. [8장](#8-보류미확인)의 미확인 항목 중 사내 환경에서 직접 확인할 수 있는 것은 확인 결과를 함께 적습니다.

이 문서 자체도 기준의 적용 대상입니다. 코드를 읽으면 알 수 있는 내용을 9장에 다시 옮겨 적지 않습니다.

## 1. 판정 기준

### 1.1 결정적 지시와 비결정적 지시

| 구분 | 수단 | 성격 |
|---|---|---|
| 비결정적 지시 (모델이 판단) | steering, 스킬, 프롬프트, 에이전트 정의의 본문 | 대부분 지켜지지만 매 턴 모델의 판단에 달려 있음 |
| 검증 수단 (판정은 기계적, 실행은 모델 의존) | Gradle test·compileJava, 비교·검증 스크립트, 그 결과 파일 | 실행되면 결과는 모델의 주장과 무관함. 그러나 모델이 실행을 생략하거나 이전 실행의 결과를 읽을 수 있음 |
| 강제 수단 (하네스가 강제) | 에이전트 권한 규칙, 빌드에 연결된 단계, pre-commit 훅, CI, MR 승인, 턴 종료를 막는 훅 | 실패하거나 실행되지 않으면 완료 전환이나 병합이 막힘 |

검증 수단과 강제 수단을 구분하는 이유는 다음과 같습니다. 검증 명령을 알려주는 것은 모델이 스스로 작업을 확인하게 해 주지만, 그 명령이 매번 실행된다는 보장은 아닙니다. 출처도 검증 명령을 적어 두는 것과 종료 시점에 검사를 강제하는 것을 별개로 다룹니다. 검증 수단을 강제로 올리려면 두 가지가 필요합니다.

- **차단.** 검사가 실패했거나 실행되지 않았을 때 완료 전환이나 커밋·병합을 막는 장치
- **증거 연결.** 결과 파일이 어느 task와 어느 코드 스냅샷을 대상으로 만들어졌는지 확인. 이것이 없으면 이전 실행의 성공 파일로 검증되지 않은 변경이 완료 처리될 수 있습니다.

사내 Kiro에서 task 완료 전환을 막는 기능은 확인되지 않았습니다([8.1](#81-사내-kiro에서-확인할-것)). 확인 전까지 위임된 task의 완료 판정은 "증거 기반 운영, 실행 강제는 미확인" 상태로 봅니다.

기본값은 모델에게 판단을 맡기는 쪽입니다. 지침에는 거의 항상 예외가 있고, 코드를 눈앞에 둔 모델이 미리 써둔 규칙보다 상황을 더 잘 판단하는 경우가 많기 때문입니다. 강제 수단은 "항상" 또는 "절대"가 필요한 규칙에만 씁니다.

판별 신호는 두 가지입니다.

- 어떤 줄에 강조를 계속 더하는데도 모델이 놓친다면, 그 줄은 강제 수단으로 옮겨야 합니다.
- 반대로 단순 선호를 강제 수단으로 걸어두었다면 지우고 모델에게 맡깁니다.

### 1.2 "코드를 읽으면 아는가" 두 질문

steering이나 스킬에 무언가를 적기 전에 두 가지를 묻습니다.

1. 코드를 읽으면 알 수 있는가?
2. 모델이 실제로 찾아볼 것인가?

둘 다 예라면 적지 않습니다. 매 세션 로드되는 줄은 관련 없는 작업에서도 모델의 주의를 조금씩 가져갑니다.

### 1.3 텍스트 보고는 완료의 증거가 아니다

Opus 5.5는 긴 작업 중에 진행 상황을 보고하며, 그 보고 중 일부는 도구 호출 없이 텍스트로 턴을 끝냅니다. 턴이 끝났다는 사실과 작업이 끝났다는 사실은 다릅니다. 완료 여부는 [5장](#5-완료-판정)의 검사와 증거로만 판정합니다.

## 2. 지울 것

steering, 스킬, 에이전트 정의 본문에서 다음 유형을 찾아 삭제 후보로 올립니다.

| 유형 | 예 | 지우는 이유 |
|---|---|---|
| 사고량 지시 | "신중하게 생각해", "단계별로 생각해", "꼼꼼히" | 모델이 사고량을 스스로 정하고, 조절 수단은 effort 설정입니다. 문구는 effort 범위 안에서 약하게 작용할 뿐입니다. |
| 추론 출력 요구 | "추론 과정을 전부 출력해" | 내부 추론을 응답에 재현하라는 요구는 거부될 수 있습니다. 짧은 근거 설명이나 수행 요약을 요청하는 것은 괜찮습니다. |
| 강조 누적 | IMPORTANT, 대문자, "반드시", "절대" 반복 | 평이한 문장으로 충분하고, 강조를 쌓으면 규칙을 과잉 적용합니다. 정말 예외가 없다면 [4장](#4-하네스로-옮길-것)으로 옮깁니다. |
| 지속 독려 | "계속해", "끝날 때까지 반복", "게으름 피우지 마" | 합의된 작업은 대개 스스로 이어가고, 이런 문구는 과잉 작업을 부릅니다. 통과해야 할 검사를 주는 것은 별개이며 유효합니다. |
| 코드에서 읽을 수 있는 설명 | 아키텍처 개요, 디렉터리 구조, 기존 컨벤션 나열 | 모델이 레포를 직접 읽습니다. [1.2](#12-코드를-읽으면-아는가-두-질문)의 두 질문을 통과하지 못합니다. |
| 품질 향상 목적의 위임 | "더 좋은 답을 위해 서브에이전트에 맡겨라" | 같은 모델에 같은 일을 넘겨도 답이 좋아지지 않습니다. 위임의 근거는 병렬성, 출력 격리, 독립된 리뷰, 도구 제한입니다. |

다음은 지우지 않습니다.

- 통과해야 할 검사와 그 실행 명령
- 범위에 대한 정보 (어디까지 만들지는 사람만 아는 정보입니다)
- 두 가지 합리적인 접근 중 팀이 고른 쪽

## 3. 남기거나 옮길 것

### 3.1 steering에 남길 네 가지

- **검증 명령.** 모듈 단위 test, 단일 테스트 클래스 실행, compileJava, SpotBugs, JaCoCo 리포트의 정확한 명령
- **코드가 오해를 부르는 지점.** 널리 퍼져 있지만 새 코드가 따라 하면 안 되는 패턴, 안 쓰는 것처럼 보이지만 쓰이는 디렉터리. 마이그레이션 프로젝트에서는 As-Is에서 넘어온 패턴이 여기에 해당합니다.
- **레포에 없는 결정.** 회의에서 정한 것, 특정인의 머릿속에 있는 절차, 통합 테스트에 필요한 환경변수
- **두 번 이상 교정한 것.**

### 3.2 범위를 좁혀 옮길 것

- 특정 경로에서만 의미 있는 규칙은 해당 경로를 다룰 때만 로드되도록 분리합니다.
- 팀 절차(릴리스, MR 대응, 스펙 승격 등)는 스킬로 옮깁니다. 스킬은 이름과 설명만 상시 노출되고 본문은 필요할 때만 읽히므로 무관한 작업에 부담을 주지 않습니다.
- 부작용이 있는 절차는 모델이 스스로 시작하지 못하게 하고 사람이 호출할 때만 실행되도록 합니다. (Kiro에서 지원하는 방식은 [8장](#8-보류미확인) 확인 항목)

### 3.3 스펙 문서에는 적용하지 않음

[1.2](#12-코드를-읽으면-아는가-두-질문)의 두 질문과 2장의 삭제 기준은 매 세션 로드되는 상시 지침(steering, 스킬, 에이전트 정의)을 줄이는 기준입니다. requirements·design·tasks에는 적용하지 않습니다. 스펙은 모델에게 주는 지침이기 전에, 구현 전에 사람이 검토하고 승인하는 계획이며 리뷰 때 "승인한 설계를 구현했는가"를 비교하는 기준입니다. 승인한 설계 결정, 제약, 작업 순서, 완료 조건은 구현 후 코드에서 읽을 수 있게 되더라도 이 가이드를 근거로 지우지 않습니다.

스펙의 분량 관리는 기존 스펙 워크플로우의 기준(5분 리뷰 가능 여부, 분할, 압축, 문서 항목 id로 추적되는 부록 이동, 반복 내용 삭제)을 따릅니다. 9장 후보 목록에 스펙 문서의 축약·삭제 항목을 올리지 않습니다.

완료된 feature 스펙을 삭제할지는 아직 검토 중이며 이 가이드의 기준이 아닙니다.

## 4. 하네스로 옮길 것

### 4.1 후보 선정 기준

- 예외가 0개인 규칙만 옮깁니다. "가급적 ~한다" 류는 steering에 둡니다.
- 강제 규칙의 수를 적게 유지합니다. 모든 강제 규칙은 가끔 잘못 발동하고, 누군가 유지보수해야 합니다. 수십 개가 되었다면 대부분은 선호일 가능성이 높습니다.
- 모델에게 판단을 묻는 방식의 훅은 강제가 아닙니다. 실제 강제에는 명령 실행형을 씁니다.
- 의미 판단이 필요한 규칙은 강제 대상이 아닙니다. 기계가 후보를 추출하고 판단은 리뷰어나 사람이 합니다. ([4.3](#43-검토할-후보)의 TR-2가 이 경우입니다.)

### 4.2 Kiro에서의 제약

Kiro 문서에 따르면 서브에이전트 안에서는 훅이 실행되지 않습니다([리뷰 단계 제안](2026-11-agent-code-review-stage.md) 참고). 태스크 수행 에이전트는 빌트인이라 설정을 바꿀 수도 없습니다. 따라서 위임된 태스크에 쓸 수 있는 수단은 다음과 같고, [1.1](#11-결정적-지시와-비결정적-지시)의 구분으로는 성격이 서로 다릅니다.

| 수단 | 구분 | 보장 범위 |
|---|---|---|
| 빌드에 연결 (Spotless를 compileJava에 연결한 방식) | 강제 | 빌드가 실행되는 한 적용됨. 빌드 자체를 건너뛰는 것은 막지 못함 |
| 커스텀 에이전트의 권한 규칙 | 강제 | 직접 정의한 에이전트(리뷰어 등)에만 가능. 빌트인 태스크 에이전트에는 적용 불가 |
| pre-commit 훅 | 강제 | 커밋 시점의 최종 방어선. `--no-verify`로 우회할 수 있으므로 그 명령 자체를 권한 규칙이나 승인 대상으로 둘지 검토 |
| 메인 에이전트가 호출하는 검증 스크립트와 결과 파일 | 검증 | 판정은 기계적이지만 호출 여부는 메인 에이전트에 달려 있음 |

검증 스크립트를 강제로 올리는 방법은 pre-commit 훅에서 결과 파일의 존재와 대상 스냅샷 일치를 확인하는 것입니다. [리뷰 단계 제안](2026-11-agent-code-review-stage.md)의 승인 스냅샷 비교가 이 방식입니다. task 단위 완료 전환을 막는 수단은 확인되지 않았으므로, task 단계에서는 결과 파일을 task와 스냅샷에 연결해 두고 커밋 시점에 강제합니다.

### 4.3 검토할 후보

| 규칙 | 현재 | 후보 수단 | 구분 |
|---|---|---|---|
| 포맷 적용 | compileJava에 연결됨 (완료) | – | 강제 |
| 리뷰어는 코드를 수정하지 않는다 | 리뷰 단계 제안의 에이전트 정의 | 권한 규칙 (fs_write deny) | 강제 |
| 완료된 스펙 디렉터리(`specs/`)를 수정하지 않는다 | 미확인 | pre-commit 비교 또는 권한 규칙 | 강제 |
| TDD task는 모듈 test 통과 없이 완료 처리하지 않는다 | task 완료 조건 (비결정적) | task·스냅샷에 연결된 검증 결과 파일. 커밋 시점에 pre-commit으로 확인 | task 단계는 검증, 커밋 단계는 강제 |
| Red 이후 테스트가 구현에 맞춰 약해지지 않는다 | 리뷰 단계 제안의 TR-2 | 스냅샷 비교로 변경 후보 추출 → 리뷰어가 스펙 근거와 검증 의미의 변경 여부 판단 | 후보 추출은 검증, 판정은 비결정적 |

마지막 행은 차단 규칙이 아닙니다. 스냅샷 비교가 확정하는 것은 "테스트가 변경됐다"는 사실뿐이고, 검증 의미가 약해졌는지는 별도 판단이 필요합니다. 헬퍼·픽스처 추출이나 이름 변경처럼 Refactor 단계의 정상적인 테스트 변경이 있으므로 변경 자체를 막으면 안 됩니다. 기존 TR-2 설계를 그대로 따릅니다.

## 5. 완료 판정

### 5.1 task 유형별 검사와 증거

모델에게 pass/fail로 돌아오는 검사를 주면 스스로 루프를 닫습니다. 검사가 없으면 "다 된 것처럼 보인다"가 유일한 기준이 되고, 사람이 테스트 스위트 역할을 하게 됩니다.

| task 유형 | 검사 | 증거 |
|---|---|---|
| 비즈니스 로직 (TDD) | 해당 서브모듈 test | 실행한 명령과 테스트 결과 리포트 |
| 인터페이스 설계·VO 생성 | compileJava | 실행한 명령과 종료 코드 |
| 최종 품질 검사 | JaCoCo 리포트, smoke test | 리포트 파일 |
| 문서 업데이트 | 기계 판정 불가 | 변경된 파일 목록과 diff, 사람 확인 |

"모든 테스트 통과"라는 문장은 증거가 아닙니다. 실행한 명령과 그 출력을 요구하고, 가능하면 메인 에이전트가 보고 대신 기계 판독 가능한 결과 파일을 직접 읽습니다.

결과 파일은 대상과 연결되어야 증거입니다. 어느 task에 대해, 어느 코드 스냅샷을 대상으로 생성됐는지 확인할 수 있어야 하고, 현재 작업 트리가 그 스냅샷과 같은지 대조합니다. 이 표의 검사는 [1.1](#11-결정적-지시와-비결정적-지시)의 검증 수단이며, 실행 강제는 [4.2](#42-kiro에서의-제약)를 따릅니다.

출처는 완료 조건을 별도의 작은 모델이 대화와 대조해 판정하는 방식도 제안합니다. 결정적으로 판정되는 task에는 결과 파일 파싱이 더 낫고, 모델 판정은 문서 업데이트처럼 기계 판정이 불가능한 task에만 고려합니다.

### 5.2 자동 재개 상한

턴이 열린 항목을 남긴 채 끝났고 막힌 이유를 밝히지 않았다면, 남은 항목의 이름을 적은 짧은 메시지로 재개시킵니다. 같은 task에서 자동 재개는 2~3회로 제한합니다. 그 이상은 실제로 막힌 것이므로 사람이 검토합니다.

백그라운드 명령이나 서브에이전트가 아직 실행 중이면 완료로 처리하지 않고 결과를 기다립니다.

### 5.3 조기 종료 패턴 명시 (무인 구간 한정)

Opus 5.5는 피해야 할 조기 종료의 구체적 유형을 지목하면 잘 따릅니다. 사람이 자리를 비우는 구간(tasks 일괄 실행 등)에만 다음 취지의 지시를 둡니다.

> 도구 호출 없이 메시지를 끝내면 작업이 멈춘다. 다음 네 가지 방식으로 턴을 끝내지 않는다.
> 1. 한 일을 길게 요약하고 다음 단계를 예고만 한 채 끝낸다.
> 2. 계속 진행해도 되는지 묻고 답을 기다린다.
> 3. 나머지 작업을 막지 않는 결정 사항 목록을 내밀고 멈춘다.
> 4. 턴이 길어졌거나 한 단계가 끝났다는 이유로 보고하기 좋은 지점이라 판단하고 멈춘다.
>
> 상태 메모와 권고는 다음 도구 호출과 같은 메시지에 적고, 사용자의 답이 필요 없는 일은 계속 진행한다. 멈춰야 하는 경우는 사용자 없이는 아무것도 진행할 수 없을 때, 그리고 막고 있는 것이 의도적으로 보호된 대상일 때뿐이다. 위험하거나 되돌릴 수 없는 작업의 확인 절차는 이 지시보다 우선한다.

적용 조건은 다음과 같습니다.

- 사람이 대화에 참여하는 구간(브레인스토밍, 스펙 작성·리뷰)에는 넣지 않습니다.
- 멈춤이 줄면 잘못된 단계를 잡을 기회도 줄어듭니다. 되돌릴 수 없는 작업의 확인 절차는 별도로 유지합니다.
- 도구 호출과 출력 토큰이 다소 늘어납니다.
- 반대 방향도 가능합니다. 대화형 구간에서는 시작 전 한 줄 계획과 종료 시 짧은 요약을 요청하면 따릅니다.

## 6. 리뷰 에이전트 요건

상세 설계는 [리뷰 단계 제안](2026-11-agent-code-review-stage.md)을 따릅니다. 이 가이드는 두 출처에서 확인된 요건만 적습니다.

- **격리.** 코드가 작성된 대화를 보지 않은 에이전트가 리뷰합니다. 작성 과정의 추론에 끌려가지 않기 위해서입니다.
- **읽기 전용.** 수정 금지는 본문 지시가 아니라 권한 규칙으로 강제합니다.
- **스펙 대비 정확성만.** 모든 요구사항이 구현되었는지, 명시된 엣지 케이스에 테스트가 있는지를 보고, 정확성에 영향을 주는 공백만 보고합니다. 스타일은 건너뜁니다.
- **지적을 전부 고치지 않습니다.** 문제를 찾으라는 요청을 받은 리뷰어는 항상 무언가를 찾습니다. 모두 반영하면 불필요한 추상화와 일어날 수 없는 경우의 테스트가 쌓입니다.
- **증거를 요구합니다.** 지적마다 파일과 줄, 틀린 이유, 실패를 보이는 방법을 적게 합니다.

## 7. 무인 실행 전 체크리스트

사람이 지켜보는 동안에는 빠진 맥락을 한두 메시지 안에 알아차리고 바로잡습니다. 무인 실행에서는 잘못된 가정 위에 작업이 계속 쌓입니다. 실행을 맡기기 전에 그 작업에 대해 다섯 가지를 확인합니다.

| # | 질문 | 우리 워크플로우에서의 답 |
|---|---|---|
| 1 | 완료가 무엇인지 아는가 | tasks.md의 완료 조건, 실패하는 테스트 |
| 2 | 스스로 검사할 수 있는가 | 모듈 test, 검증 스크립트, 리뷰 단계 |

| 4 | 무엇이 멈추는가 | 자동 재개 상한, Kiro의 턴·비용 한도 ([8장](#8-보류미확인) 확인 항목) |
| 5 | 결과가 어디로 가고 누가 승인하는가 | ELI5 HTML 확인, MR 승인 |

| 진행 상황 메모가 화면에 표시되는지 | 긴 task 실행 관찰 | Opus 5.5는 도구 호출 사이의 메모를 thinking 블록으로 보내며, 클라이언트 설정에 따라 보이지 않을 수 있습니다. |

### 8.2 채택하지 않거나 보류한 권고

| 권고 | 판단 | 이유 |
|---|---|---|
| 컨텍스트는 더 이상 주된 제약이 아니다 | 보류 | 1M 윈도우와 자동 압축이 전제입니다. Kiro 설정 확인 전에는 기존 컨텍스트 관리 관행을 유지합니다. 무관한 작업 사이에 세션을 새로 시작하는 것은 전제와 무관하게 유효합니다. |
| 완료 조건을 작은 모델이 판정 | 부분 채택 | 결정적 판정이 가능한 task에는 결과 파일 파싱을 씁니다. ([5.1](#51-task-유형별-검사와-증거)) |
| 멀티에이전트에 경과 시간·예산 신호 부여 | 미적용 | 하네스가 메시지마다 경과 시간을 붙여야 하는데 Kiro에서 수단이 확인되지 않았습니다. |
| 붙여넣은 텍스트 태그 표시, 채팅 후속 답변 고정, 멀티앱 탐색 지시, 프론트엔드 스타일 지정 | 해당 없음 | 사내 워크플로우와 무관합니다. |
| effort 수치(medium이 Opus 5 high와 동등 등) | 참고만 | Anthropic 자체 평가 결과입니다. 사내 Java/Spring 과제로 만든 회귀 세트 없이 그대로 채택하지 않습니다. |

### 8.3 이 가이드의 한계

- 출처는 Claude API와 Claude Code 기준으로 쓰였습니다. Kiro의 대응 기능으로 옮겨 읽은 부분은 사내 환경에서 검증되지 않았습니다.
- 증거 기반 완료 판정, 독립된 리뷰, 필수 규칙의 실행 강제는 모델과 무관한 원칙입니다. 반면 2장의 지침 삭제 효과는 Opus 5.5에 대해 보고된 것이므로, 다른 모델(비교 리뷰어 등)이 쓰는 지침에 일반화하려면 별도 검증이 필요합니다.
- 모델에게 판단을 넓게 맡기는 방향은 검사가 믿을 만할 때만 안전합니다. 어떤 결과가 맞는지 판정할 도메인 지식이 부족한 영역에서는 이 가이드가 해결책을 주지 않습니다. 그 영역은 브레인스토밍 단계의 AC 확정에서 다룹니다.

## 9. 적용 후보 목록

> 이 장은 사내 프로젝트를 읽은 에이전트가 작성합니다. [이 문서를 받은 에이전트에게](#이-문서를-받은-에이전트에게)의 절차를 따릅니다.

### 9.1 작성 규칙

- 한 행은 변경 하나입니다. 같은 유형이 여러 파일에 있으면 행을 나눕니다.
- "근거 위치"에는 파일 경로와 줄 번호를 적습니다.
- "기준"에는 이 문서의 절 번호를 적습니다. (예: 2, 3.1, 4.3)
- "변경"은 삭제 / 수정 / 이동(어디로) / 신규 / 확인 필요 중 하나로 시작합니다.
- "수단"은 비결정적 / 검증 / 강제 중 변경 후의 상태를 적습니다. 검증으로 적은 항목은 실행이 무엇에 의존하는지도 함께 적습니다.
- "승인" 열은 비워 둡니다. 사람이 채웁니다.

### 9.2 우선순위 기준

| 우선순위 | 대상 |
|---|---|
| P1 | 삭제만으로 끝나는 항목(2장), 완료 증거 요구(5.1). 위험이 낮고 즉시 적용 가능합니다. |
| P2 | 검증·강제 수단으로의 이전(4장), 조기 종료 패턴 지시(5.3). 동작 검증이 필요합니다. |
